# Слой: write-путь (действия, меняющие портал)

Всё, что **меняет** портал — создать задачу, отправить сообщение, прикрепить файл. Отдельно от read-слоёв, потому что ставка выше: сообщение уходит **от твоего имени** (вебхук под твоей учёткой, не бот), задача реально создаётся у человека. Поэтому всё, что затрагивает других людей, — под жёстким протоколом подтверждения. Действия, которые не задевают никого, кроме тебя, из него вынесены — развилка ниже.

Фундамент (настройка, безопасность) — в `SKILL.md` рядом.

---

## Развилка: кого действие задевает

Критерий один — **задевает ли действие кого-то, кроме тебя**.

- **Задача на самого себя** (исполнитель = ты) — выполняется сразу, одним шагом, без превью и без вопроса «можно?». Она не тратит чужого времени, не уходит от твоего имени живым людям и откатывается тобой же; ты сам её и попросил, так что лишний раунд подтверждения тут — трение, а не защита. Содержание всё равно продумывается как следует (полный контекст в описании, не строчка); не ясен срок — ставь без срока и скажи об этом, а не переспрашивай.
- **Всё, что касается другого человека** — задача на исполнителя, сообщение в личку, сообщение в общий чат — только по жёсткому протоколу ниже. Отправленное не отзывается, чужое внимание уже потрачено.

Послабление касается **только** задач на себя. Сообщения остаются под полным протоколом всегда: адресат-человек делает действие необратимым, даже когда тема кажется мелкой.

## Жёсткий протокол (для действий, затрагивающих других)

**Агент не выполняет такой write сам.** Всегда:

1. Человек просит явно («поставь задачу N по теме X», «напиши N в личку: …»).
2. Агент **резолвит получателя** через `user.get` (при однофамильцах — уточнить ID, не угадывать).
3. Агент запускает действие в режиме **превью** (dry-run) — портал НЕ трогается, показывается что именно уйдёт: кому (имя + ID), текст, вложения.
4. Агент показывает превью человеку **в чате** одним блоком.
5. Человек подтверждает или правит («да, отправляй» / «отмени» / «измени текст»).
6. Только после явного «да» — реальный вызов. Вернуть ID созданного объекта.

Не запускай реальный вызов сам, без шага 5. Не выполняй «по умолчанию».

> **Совет ≠ команда.** Если в разговоре ты (владелец) обронил «надо бы написать N» / «стоит поставить задачу» — это **обсуждение**, а не команда на отправку. Агент выполняет write только на явную инструкцию, не на пересказ намерения.

## Создать задачу — `tasks.task.add`

Превью → подтверждение → создание. Возвращается ID задачи.

**Прикрепить файл** (нужен scope `disk`):
- Файл сначала грузится на Диск (`disk.folder.uploadfile`), потом привязывается к задаче через поле файлов задачи (хранит ID объекта на Диске, не сам файл).
- Загрузка идёт **до** создания задачи — если файл не загрузился, задача не создаётся (нет половинчатого результата).
- Гоча: метод листинга хранилищ Диска на крупном портале **всегда с фильтром** по личному хранилищу владельца — без фильтра он перечисляет тысячи хранилищ подчинённых и висит дольше лимита запроса.

## Отправить сообщение — `im.message.add`

Приватный канал «не через задачу»: в задачу всегда может дописаться наблюдатель, а личный диалог двух людей закрыт. Та же команда шлёт и в личку, и в групповой/проектный чат — разница в адресате:

- **Личка** — адресат = ID пользователя (приватный диалог один-на-один).
- **Группа / проект** — адресат = `chat<id>` (сообщение видят **все** участники, не приватно). В группе можно **тегнуть** человека упоминанием-BBCode `[USER=<id>]Имя[/USER]` (ID — через `user.get`) — отрендерится кликабельным пингом.

Файлы уходят нативным вложением (грузятся на Диск → коммитятся в диалог), не голой ссылкой.

**Оговорка приватности** (проговаривать, если тема чувствительная): приватно ОТ КОЛЛЕГ — никто не вклинится в личный диалог. Но корпоративный портал — не end-to-end: у администратора есть доступ к логам мессенджера. Для приватности от самой компании это не тот канал.

## Изменить состав участников задачи — `tasks.task.update`

Добавить наблюдателя или соисполнителя в **уже созданную** задачу (при постановке они задаются сразу, это про потом). Операция выглядит безобидно — «подключить одного человека», — но это самая коварная форма write: портал ведёт себя не так, как читается запрос.

🔴 **Поле участников перезаписывается ЦЕЛИКОМ.** Отправив список из одного id, ты не добавляешь наблюдателя — ты объявляешь, что наблюдатель теперь ровно один. Все прежние молча выпадают из задачи, портал отвечает успехом, и заметит это только тот, кто перестал получать уведомления. Ни исключения, ни предупреждения: ошибка не диагностируется вообще.

Правильная форма — **read-modify-write**:

1. прочитать текущий состав (`tasks.task.get` с явным select по нужным полям);
2. посчитать целевой список: объединение с текущим при добавлении, вычитание при снятии;
3. отправить **весь** целевой список;
4. **перечитать задачу и сверить** — и только после совпадения говорить «готово».

Шаг 4 не формальность. Молчаливый неуспех здесь дороже явной ошибки: человек, услышав «добавил», считает, что коллега в задаче и всё видит, а узнаёт правду через неделю — когда окажется, что тот ничего не получал.

Две мелочи, на которых ломаются реализации:

- **Форма ответа плавает.** Список участников приходит то массивом строк, то массивом чисел, то объектом с индексами-ключами — зависит от версии метода. Разбирай защитно и не «падай на неожиданном»: потерянный при разборе id означает выкинутого из задачи человека.
- **«Нечего менять» — не повод звать портал.** Если все названные уже в задаче, целевой список равен текущему: не отправляй запрос вовсе. Это бесплатная идемпотентность и на один шанс перезаписать состав меньше.

**Упоминание ≠ участие.** Тегнуть человека в чате задачи (`[USER=<id>]`) — не то же самое, что добавить его в наблюдатели: пинг придёт, но задача не появится у него в списках и уведомления по ней ходить не будут. Просьбу «добавь N в задачу» закрывает состав, а не упоминание — подмена выглядит выполненной и не работает.

> Это общий класс, а не частность задач. То же верно для любого поля-коллекции, которое API принимает целиком: участники группы, теги, списки доступа. Признак — **в запросе список, а в голове действие «добавить одного»**. Увидел такой разрыв — пиши read-modify-write и сверку, даже если сегодня в поле пусто.

## Про лимит времени на вызов

Если агент работает в песочнице с потолком на один вызов и без переживающих вызов фоновых процессов — write-операция должна уложиться в **один** вызов (загрузка файла + создание за раз). Долгие фоновые прогоны с поллингом лога там не работают — не рассчитывай на них для write.
